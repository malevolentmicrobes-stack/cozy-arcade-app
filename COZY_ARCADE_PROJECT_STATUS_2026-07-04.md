## Neural pulse v3 — fixed a self-inflicted feedback loop, true viewport-top position, breathing star (v106→v107)
User reported "still flashing present" on live v106 and asked for (a) genuine top-of-viewport position independent of screen size, and (b) a smooth breathing-star cycle (like a CLI spinner: `·✢✶✻✽✻✶✢·`) instead of any abrupt swap. Root-caused the "still flashing": v2 was fine on its own, but repositioning to `position:fixed` led me to append the element directly to `document.body` — which re-triggered an **already-existing** `MutationObserver` on `document.body`'s direct children (childList, non-subtree, line ~13141) that debounce-calls `run()` at ~800ms. `run()` re-adds the `game-shell` class to `#solo`/`#domain` (`renderHudControls`), which this feature's own `watchGame()` observer also reacts to (filters on the whole `class` attribute, not just `hidden`) — creating a self-sustaining eject→inject loop. Measured directly: the element's existence flickered true/false roughly every 800-900ms, confirmed via a 20-sample/2-second continuity check before and after the fix (all `false` cycles gone after the fix, 20/20 `true`).

Fix: append inside `#solo`/`#domain` instead of `document.body` — `.game` has no `transform`, so `position:fixed` children still measure from the true viewport (same visual result), and insertion no longer triggers the problematic body-childList observer. Also added: smooth opacity crossfade on both the star (breathing through `·✢✶✻✽✻✶✢·` every ~420ms) and the main text (fades on the 12s idle refresh and on rating feedback) — no instant content swap anywhere now, matching the "gradation, not flashing" request directly.

Live-validated: 20/20 continuity samples over 2s (no more disappear/reappear), star opacity sampled mid-transition (0.21–0.99 range, confirming genuine crossfade not instant swap), position `fixed` at viewport `y:0` on both mobile and desktop, screenshot-confirmed clean at idle and immediately after rating (fireworks still visible, kept per earlier decision), FSRS 17/17, smoke 6/6, zero page errors.

**Standing lesson for this file:** `document.body`'s direct children are watched by at least one pre-existing `MutationObserver` tied into the `run()`/`renderHudControls` cycle. Any future code appending directly to `document.body` (not a descendant container) should check for this specific interaction first — it's an easy, non-obvious way to create a self-sustaining re-render loop.

## Neural pulse reimplemented (v2) — flashing removed, informative content kept, position fixed (v105→v106)
User clarified: wanted the flashing mechanics gone, not the informational text — "the text was cool, just wrong place." Reimplemented from scratch, keeping the exact same content (session time, due count, energy, per-rating stability/next-interval feedback) but removing everything that caused the original flicker complaint: no `.flash` color-transition class, no 4-character rotating-star cycling (replaced with one static `✳`). Repositioning took 3 iterations, each caught by live measurement rather than assumed:
1. First attempt: `top:0` inside `#solo`/`#domain` directly — visually collided with the HUD icon row (mobile HUD is a dynamic, content-dependent 117px-tall block, taller than assumed, leaving no free gap before the prompt box).
2. Second attempt: docked inside `.promptBox` as a normal-flow first child with `margin-bottom` spacing — measured actual gap to the system badge was **-5px** (real overlap) despite the margin value, because `.systemBadge` is `position:absolute!important` and completely ignores document flow/sibling margins.
3. Final: made the pulse element `position:absolute` too (same positioning context as the badge), anchored above it at `top:3px`. Measured gap to badge: **+2px** (clean). Zoomed screenshot confirmed genuinely no overlap — an earlier full-page screenshot had made a real 2px gap look like zero due to image-scaling compression, not an actual bug.

Live-validated both mobile (390×844) and desktop (1280×900) viewports via screenshot: text renders clean, legible, above the system badge and question, no flash class ever applied (checked directly on the DOM node after a rating), FSRS 17/17, smoke 6/6, zero page errors. Domain mode uses an identical `.promptBox` structure so the same fix applies there without separate positioning logic.

**Lesson for any future HUD/prompt-box layout work in this file:** several key elements (`.systemBadge`, likely others) are absolutely positioned with `!important` and completely opt out of normal document flow — a sibling's margin/padding has zero effect on them. Always measure actual rendered gaps (`getBoundingClientRect()`), never assume CSS box-model reasoning alone predicts the result in this codebase.
